# Database Architecture & Tables

## Overview
The system uses a hybrid database approach:
1. **Oracle Database**: The source of truth for backend/dashboard data, employees, vehicles, single sign-on users, trips, GPS points, stops, audit logs, and the integrated wells module.
2. **Mobile Local Storage**: Flutter apps may store offline records locally before syncing. The Laravel dashboard/backend must not depend on local SQLite data.

## Managed Tables (Created via Laravel Migrations)

### `trips`
The core entity representing a single vehicle journey.
- `id`: Primary key.
- `local_id`: UUID generated by the mobile app. Used as an idempotency key.
- `oracle_driver_id`: The ID of the driver in the Oracle database.
- `driver_id`: (Optional) Local driver ID if using local caching.
- `oracle_vehicle_id`: The ID of the vehicle in the Oracle database.
- `vehicle_id`: (Optional) Local vehicle ID.
- `vehicle_plate`, `vehicle_name`, `vehicle_type`: Snapshots of vehicle details at the time of the trip.
- `driver_name`, `driver_phone`, `driver_employee_number`: Snapshots of driver details at the time of the trip.
- `status`: `uploaded` (still receiving points) or `confirmed` (all points received and checksum matches).
- `review_status`: `pending` (default), `approved`, `rejected`, or `needs_clarification`.
- `review_note`, `reviewed_at`, `reviewed_by`: Audit trail for the administrative review.
- `clarification_response`, `clarification_responded_at`: Driver's response to a clarification request.
- `started_at`, `ended_at`: Timestamps for the trip duration.
- `confirmed_at`: Timestamp when the trip was marked as confirmed.
- `origin_type`, `origin_id`, `origin_text`: Start location details.
- `destination_type`, `destination_id`, `destination_text`: End location details.
- `mission_type`: The type of mission (e.g., maintenance, fuel).
- `notes`: Any notes left by the driver.
- `start_odometer`, `end_odometer`: Odometer readings.
- `points_expected`: The total number of GPS points the app expects to upload.
- `points_received`: The exact server-maintained count of unique stored GPS rows. Batch upload and confirmation refresh it from `TRIP_POINTS`; dashboard visibility may read this counter without rescanning the full points table.
- `client_checksum`: The SHA256 checksum generated by the mobile app.
- `server_checksum`: The SHA256 checksum calculated by the server to verify integrity.
- `wait_minutes`: The total number of minutes the vehicle was waiting during the trip.
- `virtual_fuel_liters`: Estimated fuel consumption calculated from GPS data.
- `distance_km`: Server-confirmed trip distance. Quality-v2 trips store filtered distance; legacy confirmation uses the legacy/recorded policy when quality metadata is insufficient.
- `duration_minutes`: Server-confirmed trusted duration, capped by the trip-duration guardrail.
- Conservative gap estimates are not columns on `TRIPS`. `estimated_gap_distance_km`, `estimated_distance_with_gaps_km`, `estimated_fuel_with_gaps_liters`, and estimable/unestimable counts are derived read-only for the admin trip-details Inertia response. Never migrate, backfill, or report them as official values without a separately approved audited persistence policy.

### `trip_points`
Individual GPS coordinates forming the path of a trip.
- `trip_id`: Foreign key to `trips`.
- `sequence_number`: The order of the point. Used as an idempotency key.
- `latitude`, `longitude`: Coordinates.
- `accuracy`, `speed`, `heading`, `battery_level`, `provider`: Telemetry data.
- `captured_at`: Timestamp when the point was recorded by the device.
- Unique key `(trip_id, sequence_number)` is the idempotency constraint used by Oracle batch upsert.
- The same unique key is the route-preview sampling access path: after eligible count/min/max, Oracle fetches at most 100 targeted sequence values instead of returning every coordinate to PHP.
- Performance index `(trip_id, recorded_at)` supports recent-point/freshness lookup without scanning unrelated trips.

### Fleet Tracking Performance Indexes

Migration `2026_08_24_000024_add_trip_tracking_performance_indexes.php` adds:
- `TRIPS.STARTED_AT`, `(STATUS, STARTED_AT)`, and `(ENDED_AT, POINTS_RECEIVED)` indexes for dashboard periods, fuel aggregation, and visibility.
- `TRIP_POINTS(TRIP_ID, RECORDED_AT)` for per-trip latest-point lookup.
- `TRIP_TRACKING_EVENTS(TRIP_ID, EVENT_TYPE)` and `(TRIP_ID, DETECTED_AT)` for event counts and latest-event lookup.

The migration was applied to production in batch 30 on 2026-08-24 while the global operational switch temporarily paused field synchronization. Building the indexes over 2,784,917 `TRIP_POINTS` rows took about two minutes; all six indexes were verified `VALID` before services reopened.

### `personal_access_tokens`

- Mobile tokens must store one exact ability: `driver`, `wells`, or `scada`; new mobile tokens must never use `*`.
- Migration `2026_08_26_000025_scope_mobile_access_tokens.php` updates current and recognized legacy tokenable model names in place. The token hash/identifier is unchanged, preserving installed-app sessions.
- Route middleware also validates the authenticated tokenable model, so an unknown or wildcard token cannot cross mobile-system boundaries.

### `trip_stops`
Periods where the vehicle was stationary during a trip.
- `trip_id`: Foreign key to `trips`.
- `local_id`: Nullable client UUID. New clients use it for idempotent stop updates; null preserves legacy rows.
- `started_at`, `ended_at`: Duration of the stop.
- `latitude`, `longitude`: Nullable stationary-cluster anchor displayed on the trip map.
- `source`: `automatic` for the new stationary detector, otherwise `manual` for legacy/manual records.
- `reason`, `notes`: Why the vehicle stopped.

### `trip_tracking_events`
Observed device/tracking state transitions attached to a trip.
- `trip_id`: Foreign key to `trips`.
- `local_id`: Client UUID, unique per trip for retry-safe updates.
- `event_type`: Allowlisted GPS, permission, airplane, shutdown/boot, battery, gap, clock, or tracking-error code.
- `detected_at`: Device observation time.
- `latitude`, `longitude`: Nullable last available position.
- `details_json`: Nullable small diagnostic payload.
- These rows document technical evidence; they do not encode driver intent.

### `trip_passengers`
People accompanying the driver.
- `trip_id`: Foreign key to `trips`.
- `name`: Passenger name.
- `employee_id`: (Optional) Employee number if the passenger is a municipality employee.
- `source`: How the passenger was added (`free_text`, `employee_list`, `manual`).

### `audit_logs`
An append-only log of all administrative actions.
- `trip_id`: Foreign key to `trips`.
- `action`: What was done (`approved`, `rejected`, `clarification_requested`).
- `note`: Why it was done.
- `performed_by`: Name of the administrator.

### `mission_locations` & `mission_types`
Lookup tables for populating dropdowns in the driver app.
- `name`: Display name.

### `sms_login_codes`
Temporary table for handling SMS OTP authentication.
- `phone`: The driver's phone number.
- `code`: The 6-digit OTP.
- `expires_at`: Expiration timestamp.
- `used_at`: When the code was consumed.

### `driver_app_installations`

Tracks adoption of the Android driver app without relying on mutable Oracle driver data for history.
- Unique identity: `(oracle_driver_id, device_id)`, where `device_id` is a random UUID created once by that app installation.
- Driver snapshot: `driver_name`, `driver_phone`, and `driver_employee_number`, derived only from the authenticated `Beneficiary`.
- Release data: `app_version`, numeric `build_number`, and `package_name`.
- Installation provenance: nullable `installer_store`; recognized Android store package IDs are store installs and other non-empty IDs are external installs.
- Android package times: nullable `installed_at` and `app_updated_at`.
- Activity times: immutable `first_seen_at` and refreshed `last_seen_at`.
- This table stores no GPS coordinates. Current vehicle assignment is read live through `MunicipalityVehicleRepository`; the dashboard may show a latest-trip vehicle snapshot only as fallback context.
- Fleet performance KPIs use distinct `oracle_driver_id` values from this table as the app-usage eligibility set. Active driver/vehicle status is then checked live in `G_STORE.BENEFICIARIES` and `G_STORE.VEHICLE`; do not infer active status from the presence row itself.

### `system_operational_states`

Stores the global administrative runtime switch separately from user permissions.
- `id`: Identity primary key.
- `scope`: Unique scope key; the implemented row uses `global`.
- `is_suspended`: `1` stops normal portal/system routes and every field-app API; `0` permits normal processing.
- `reason`: Required user-facing reason while suspended; cleared when systems reopen.
- `changed_by_user_id`, `changed_by_name`, `changed_at`: Latest SSO actor and change audit snapshot.
- Reads fail open when Oracle or the table is unavailable. Updates fail visibly; never infer suspension from a database outage.
- Migration: `2026_08_24_000023_create_system_operational_states_table.php`.

### Fleet Dashboard Official Fuel Aggregation

- Source column: persisted `TRIPS.VIRTUAL_FUEL_LITERS` only.
- Eligible rows: `TRIPS.STATUS = 'confirmed'`, non-null official fuel, `STARTED_AT` inside the selected dashboard range, and allowed by the dashboard experimental-trip visibility rule.
- Excluded values: provisional `distance × 0.12` driver/detail fallbacks and transient conservative gap estimates.
- The dashboard returns both the rounded liter sum and the number of contributing confirmed trips so the KPI states its coverage.

## Oracle Driver & Vehicle Source Tables (CONTROL_UNIT)

### `SYSTEM_PERMISSIONS`
Central per-system access table for the unified portal.
- `id`: Primary key.
- `user_id`: SSO user ID from `mog_users.users_list` (`id` column, NOT `emp_id`).
- `system_key`: One of `fleet`, `wells`, or `valves`.
- Sensitive Wells action keys also use this column: `wells.readings.delete` and `wells.diesel-inventories.delete`; both depend on base `wells` access.
- `granted_by`: Display name or identifier of the admin who granted access.
- `granted_at`: Oracle-side grant timestamp.
- Used by `SystemPermissionRepository`, `PortalController`, and `EnsureSystemAccess`.
- This table controls access to each integrated system independently; do not use `FLEET_ADMIN_ALLOWLIST` for per-system decisions.
- System-access checks may fail open during initial Oracle setup, but destructive action-permission checks always fail closed.
- **CRITICAL NOTE**: The `mog_users.users_list` table contains both `id` (Primary Key) and `emp_id` (Employee ID). The MOG SSO system logs users in using their `id`. Therefore, `SYSTEM_PERMISSIONS.user_id` MUST store the SSO `id`, not `emp_id`. Production example: `رامي عيد سليم غياضة` logs in as `id = 140`, `emp_id = 2541`; permissions must be granted to `USER_ID = 140`. Do not grant by similar display names such as the separate `id = 1061` row.
- Permission-screen SSO searches must filter `MOG_USERS.USERS_LIST.IS_ACTIVE = 1`; inactive users cannot receive new assignments.

### `FLEET_USERS`
Read through `MunicipalityDriverRepository`, `MunicipalityVehicleRepository`, and `Beneficiary`.
- `ID`: Driver row ID used as the authenticated Oracle driver ID.
- `USER_MOBILE`: Driver phone number.
- `USER_NAME`: Driver display name.
- `USER_ID`: Driver employee/user number snapshot.
- `VEHICLE_ID`: Assigned vehicle ID.
- `VEHICLE_NO`: Assigned vehicle plate/number.
- `VEHICLE_MODEL`: Assigned vehicle name/model snapshot.
- `VEHICLE_TYPE`: Assigned vehicle type snapshot.
- Driver app vehicle lists must filter by the authenticated `FLEET_USERS.ID`; never return an unscoped vehicle list to an authenticated driver.

### `MOG_VEHICLES`
Available in `CONTROL_UNIT` as a general vehicle reference table.
- `ID`: Vehicle ID.
- `PLATE`: Plate/vehicle number.
- `MODEL`: Vehicle model.
- `TYPE`: Vehicle type.
- Do not use `MOG_VEHICLES` for driver-scoped vehicle assignment unless a verified relationship to `FLEET_USERS` is added.

## Integrated Wells Module
The wells module has its own AI context under `.ai/modules/wells/`.
- Read `.ai/modules/wells/project-overview.md` before changing wells workflows.
- Read `.ai/modules/wells/database/tables.md` before changing wells tables or Oracle integrations.
- External wells generator/quarter references may use schemas such as `G_STORE` and `GAZADATA`; keep that context scoped to the wells module unless the fleet code explicitly needs it.
- `WELL_READINGS` and `DIESEL_INVENTORIES` retain audited soft-deletion metadata (`DELETED_AT`, `DELETED_BY_USER_ID`, `DELETED_BY_NAME`, `DELETE_REASON`). Default queries exclude these rows; see the Wells module database context for chronology and sync rules.
- Wells production reports use only consecutive `WELL_READINGS.GENERATOR_HOURS_READING` values for operating hours and multiply their non-negative difference by `WELLS.CAPACITY`; `PUMP_HOURS_READING` and `FLOW_RATE` are not fallback sources.

## Integrated Valves Module
The valves module manages municipality valves operations and maintenance logs.
- Valve source data is read from external Oracle table `EME.WATER_VALVES`; do not create or repopulate a local `VALVES` table.
- `App\Models\Valves\Valve` maps to `EME.WATER_VALVES` with primary key `W4_GENERAL_ID` and avoids selecting the Oracle Spatial `GEOMETRY` column by default.
- `ValveRepository::forMap()` transforms `GEOMETRY` to WGS84 without selecting the spatial object through normal PDO hydration. `ValveService::getMapValves()` excludes missing coordinates and values outside the Gaza bounding box before serializing the web-map payload; outliers are neither modified nor deleted in Oracle.
- Managed features in `CONTROL_UNIT`: `VALVE_LOGS`, `VALVE_MAINTENANCE_REPORTS`, `VALVE_TEAMS`, `VALVE_TEAM_VALVES`, `VALVE_INSPECTORS`, and `VALVE_INSPECTOR_TEAMS`.
- `VALVE_LOGS.CLIENT_LOCAL_ID` is nullable for legacy SCADA compatibility. Unique `(USER_OID, CLIENT_LOCAL_ID)` makes supplied offline-action IDs idempotent without causing collisions between inspectors.
- `VALVE_OID` columns store `EME.WATER_VALVES.W4_GENERAL_ID`; they are not foreign keys to a local `VALVES` table.
- Context is located under `.ai/modules/valves/`.
- Valve teams and inspectors are separate from wells teams and inspectors. Do not use wells tables for valves assignments or valve app accounts.
