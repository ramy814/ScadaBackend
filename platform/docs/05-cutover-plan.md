# 05 — خطة الاستغناء عن النظام القديم والانتقال الكامل إلى المنصة

> الهدف: أن تصبح المنصة (`platform/`) هي النظام الوحيد للويب **ولواجهات تطبيقات Flutter الثلاثة**،
> ثم إيقاف النظام القديم وأرشفته، دون توقف الخدمة، ودون فقدان رحلات محفوظة على الهواتف، ومع إمكانية الرجوع في كل مرحلة.
>
> الحالة عند كتابة الخطة (commit `bb3417c`): كل شاشات الويب منقولة؛ واجهات الموبايل ما زالت في النظام القديم فقط.
>
> **قرارات صاحب المشروع (2026-11-03، ثانية):** نظام المحابس غير مستخدم حالياً، فلا يُصلح فيه شيء الآن (الملاحظات أدناه تبقى للمستقبل) · دخول السائق يستمر بالرمز `000000` (`SMS_TEST_CODE=000000` على خادم المنصة) إلى حين ربط مزود SMS · صاحب المشروع يدير الخادم بنفسه.
>
> **قرارات صاحب المشروع (2026-11-03):** نفس المبدأ ونفس الدومين ونفس العناوين ✅ · لا يوجد مزود SMS حالياً · لا توجد قاعدة Oracle تجريبية · المرحلة 0 للويب: فحصها صاحب المشروع على Oracle وتعمل.

### ملاحظات وُجدت أثناء نقل المحابس (تخص النظام القديم في الإنتاج)
1. `GET /api/valves/{valve}` و`/logs` يفشلان دائماً في القديم (علاقة `logs.user` غير معرفة)، و`GET /api/valve-maintenance` يفشل عند وجود بلاغات (يختار عمود `id` غير موجود)، وإغلاق بلاغ يحفظ `RESOLVED_BY` فارغاً. **المنصة تجيب عنها بالشكل الذي قصده الكود** (لا يوجد تطبيق يعتمد على رد لم يصله أبداً).
2. علاقتا `Valve::logs()` و`latestLog()` تستخدمان المفتاح `VALVE_OID` بينما يُرجع Oracle الأعمدة بأحرف صغيرة، لذلك يصل `LATEST_LOG` فارغاً في قائمة التطبيق و`LOGS` فارغة في تفاصيل المحبس **في الإنتاج اليوم**. المنصة تطابق هذا السلوك حالياً؛ إصلاحه يغيّر ما يراه المفتشون (حالة آخر عملية) ويحتاج قراراً ليُطبق في النظامين.
3. سجل التغييرات في القديم يذكر أن الـ migrations `000025` (حصر صلاحيات التوكنات) و`000026` (عمود `CLIENT_LOCAL_ID` على `VALVE_LOGS`) **لم تُشغَّل** على Oracle. يجب التحقق: إن لم يكن العمود موجوداً فتسجيل عمليات المحابس يفشل في النظامين.

### دخول السائق دون مزود SMS (قرار التنفيذ)
لا يوجد مزود حالياً، فالمنصة تُبقي آلية القديم نفسها مع إغلاق الثغرتين:
- الرمز الثابت **لا يُقبل افتراضياً**؛ يُقبل فقط إذا ضُبط `SMS_TEST_CODE` صراحة على الخادم (القديم كان يقبل `000000` تلقائياً).
- ترويسة `X-Driver-Debug` أُزيلت؛ التفاصيل تذهب لسجل الخادم فقط.
- **قبل تحويل `/api/driver` يجب ضبط `SMS_TEST_CODE`** وإلا لن يستطيع السائقون الدخول (لأن القديم يعمل اليوم بالرمز الثابت فعلياً). يُفضَّل قيمة غير `000000` تُبلَّغ للسائقين، إلى حين ربط المزود.

## 1. المبدأ الذي تقوم عليه الخطة

1. **نفس قاعدة Oracle ونفس الجداول.** لا نقل بيانات؛ النظامان يقرآن ويكتبان نفس الصفوف، لذلك الرجوع آمن في أي وقت.
2. **نفس عناوين الـ API ونفس شكل الـ JSON ونفس التوكنات.** تطبيقات الموبايل لا تُعدَّل ولا تحتاج إصداراً جديداً.
   هذا مهم لأن التطبيقات تعمل دون إنترنت: سائق على إصدار قديم أو رحلة محفوظة منذ أيام يجب أن تُرفع بنجاح بعد الانتقال.
3. **نفس النطاق (الدومين).** التحويل يتم في الـ reverse proxy (nginx) مساراً بمسار، والرجوع هو إعادة السطر كما كان.
4. **تجميد التطوير على القديم** من بداية المرحلة 2: أي ميزة جديدة تُبنى في المنصة فقط (تجربة المطالبات المالية أثبتت كلفة البناء مرتين).

## 3. شروط حاجبة يجب حلها قبل نقل الـ API

### 3.1 دخول السائق برمز ثابت (أمني — عاجل، يخص القديم الآن)
`SmsAuthService` **لا يرسل رسالة SMS أصلاً** (`TODO: Integrate the municipality SMS provider`)، ويقبل رمزاً ثابتاً
`services.sms.test_code` قيمته الافتراضية `000000`، ويعود إلى `000000` حتى لو تُرك المتغير فارغاً.
النتيجة: من يعرف رقم جوال سائق مسجل يستطيع الدخول باسمه (إلا إذا ضُبط `SMS_TEST_CODE` على الخادم بقيمة أخرى — وحتى عندها هو رمز واحد مشترك لكل السائقين).
كذلك ترويسة `X-Driver-Debug: lookup` تُرجع تفاصيل أخطاء قاعدة البيانات وبيانات المنتفع لأي متصل يرسلها، في أي بيئة.
**القرار المطلوب:** ربط مزود SMS البلدية. **لن يُنقل هذا السلوك إلى المنصة كما هو**؛ المنصة تُبنى بإرسال حقيقي، ويبقى الرمز التجريبي محصوراً في البيئة المحلية.

### 3.2 التوكنات الحالية يجب أن تبقى صالحة
توكنات Sanctum مخزنة في Oracle مع اسم صنف النموذج القديم في `tokenable_type`: `App\Models\Beneficiary` (السائق)، `App\Models\Wells\Inspector` (الآبار)، `App\Models\Valves\ValveInspector` (المحابس).
المنصة يجب أن تتعرف على نفس الأسماء (morph map) حتى لا يُطلب من كل سائق ومفتش تسجيل الدخول من جديد. يُغطى باختبار.

### 3.3 تجربة الويب على Oracle الحقيقي و SSO
البندان المعلقان في `04-roadmap.md`: تجربة كل شاشة على قاعدة تجريبية، وتثبيت حزمة `mog/project-helper` على الخادم.

## 4. المراحل

### المرحلة 0 — التحضير (1–2 أسبوع)
- خادم staging للمنصة على Oracle تجريبي (أو الحقيقي للقراءة فقط) + حزمة SSO + `LEGACY_MEDIA_ROOT` + GeoServer.
- مسار نشر (CI) للمنصة مماثل لنشر القديم.
- مراجعة كل شاشة مع مشرف من كل نظام، وإصلاح الفروق (كما حدث مع السولار وصفحة الرحلة).
- **الخروج:** كل الشاشات تعمل على Oracle، والمشرفون وقّعوا على المطابقة.

### المرحلة 1 — نقل الويب (1–2 أسبوع، بالتوازي)
- نشر المنصة على المضيف الإنتاجي، وتحويل روابط لوحة الإدارة في nginx إلى المنصة؛ `/api/*` يبقى للقديم.
- أسبوع تشغيل متوازٍ: القديم متاح على رابط احتياطي للمقارنة.
- **الرجوع:** إعادة توجيه الويب للقديم (نفس البيانات).
- **الخروج:** لا بلاغات مطابقة لأسبوع كامل.

### المرحلة 2 — نقل واجهات الموبايل (3–5 أسابيع)
بالترتيب الأقل خطراً أولاً:
1. **المحابس** (`/api/valves/*`): الأصغر، والخدمة منقولة.
2. **الآبار** (`/api/wells/*`): نقل `MobileSyncService` حرفياً مع اختباراته (المزامنة idempotent بـ `CLIENT_LOCAL_ID`).
3. **السائق** (`/api/driver/*`): نقل `TripSyncService` وقواعد Offline-first حرفياً
   (لا تُحذف رحلة محلية إلا بعد الحفظ + النقاط + العدد + checksum)، ودخول SMS حقيقي (3.1)، وبلاط الخرائط.

لكل تطبيق:
- نقل اختبارات القديم (`TripPointBatchUploadTest`, `MobileTokenAbilityTest`, `MapTileTest`, `TripLiveTelemetryTest`, …) دون تعديل توقعاتها.
- **اختبار عقد:** نفس الطلبات تُرسل للنظامين على staging وتُقارن الاستجابات حقلاً بحقل.
- تجربة بأجهزة اختبار حقيقية، بما فيها رحلة محفوظة دون إنترنت ثم رفعها بعد التحويل.
- **الخروج:** الاختبارات والعقود متطابقة، وتجربة الأجهزة ناجحة.

### المرحلة 3 — تحويل الـ API (2–4 أسابيع مراقبة)
- تحويل `/api/*` في nginx تطبيقاً بتطبيق (المحابس ← الآبار ← السائق)، مع مراقبة الأخطاء ومعدل المزامنة الناجحة.
- النظام القديم يبقى منشوراً وجاهزاً للرجوع طوال فترة المراقبة.
- **الرجوع:** إعادة سطر nginx للتطبيق المعني؛ التوكنات والبيانات مشتركة فلا يتأثر المستخدم.
- **الخروج:** أسبوعان دون رجوع ودون فقدان رحلات.

### المرحلة 4 — الإيقاف والأرشفة (1 أسبوع)
- نقل ملكية المخطط: نسخ الـ 55 migration **بنفس أسمائها** إلى المنصة (يبقى جدول `migrations` في Oracle متسقاً)، وإلغاء قاعدة "لا migrations" من `AGENTS.md`.
- نقل الصور من `storage/app/private` إلى تخزين المنصة وإلغاء `LEGACY_MEDIA_ROOT`.
- حذف `public/wms.php` وكل أدوات التصحيح (`X-Driver-Debug`).
- **تغيير الأسرار** التي وُجدت مكتوبة في كود القديم (سر عميل SSO في `config/mog-helpers.php`، كلمة مرور GeoServer في `config/geoserver.php`)، وكلمة مرور Gitea التي ظهرت في عنوان `origin`.
- أرشفة القديم بـ tag (`legacy-final`) ثم نقل محتوى `platform/` إلى جذر المستودع، وتحديث `AGENTS.md`/`.ai/` وخريطة graphify.
- إيقاف خادم القديم بعد آخر نسخة احتياطية.

## 5. المخاطر وطريقة التعامل معها

| الخطر | التخفيف |
|---|---|
| رحلات محفوظة على الهواتف لا تُرفع بعد التحويل | نفس العناوين والعقد والتوكنات؛ اختبار جهاز بإصدار قديم ورحلة مؤجلة قبل كل تحويل |
| اختلاف قاعدة عمل بين النظامين أثناء الفترة الانتقالية | تجميد التطوير على القديم؛ أي إصلاح عاجل يُطبَّق في الاثنين |
| فروق Oracle لم تظهر على SQLite (مثل ORA-01795) | المرحلة 0 على Oracle حقيقي؛ اختبارات بحجم بيانات حقيقي |
| خروج كل المستخدمين بسبب التوكنات | morph map + اختبار بتوكن حقيقي من staging |
| كلفة إرسال SMS أو تأخر ربط المزود | يبدأ ربط المزود فوراً لأنه مشكلة أمنية في القديم أصلاً |

## 6. القرارات المطلوبة من صاحب المشروع

1. الموافقة على مبدأ **نفس الدومين ونفس عقود الـ API** (الموصى به) بدل دومين جديد يتطلب إصدارات جديدة للتطبيقات.
2. مزود SMS البلدية وبيانات ربطه (وإيقاف الرمز الثابت في القديم الآن).
3. وجود قاعدة Oracle تجريبية للمرحلة 0، أو الموافقة على تجربة قراءة فقط على الحقيقية.
4. بداية تجميد التطوير على النظام القديم.

> التقديرات الزمنية تقريبية لفريق صغير، وتعتمد أساساً على سرعة توفير staging ومزود SMS.

## 7. تشغيل المرحلة 3 (التحويل) — ما يلزم على الخادم

1. نشر المنصة على نفس الخادم (مجلد مستقل) بنفس اتصال Oracle، و`APP_TIMEZONE` المطابق، و`LEGACY_MEDIA_ROOT` = `storage/app/private` للقديم (صور الآبار)، وبيانات GeoServer (بلاط الخرائط)، و`SMS_TEST_CODE`.
2. التوكنات لا تعتمد على `APP_KEY` (تُخزن sha256 في `PERSONAL_ACCESS_TOKENS`)، لذلك الجلسات الحالية تعمل على المنصة فوراً، ويمكن الرجوع للقديم دون خروج أحد.
3. التحقق من حالة migrations القديم `000025` و`000026` على Oracle (انظر الملاحظة 3 أعلاه).
4. التحويل في nginx تطبيقاً بتطبيق؛ مثال (يُعدَّل حسب إعداد الخادم):

```nginx
# المحابس أولاً
location ~ ^/api/(valves|dashboard|valve-maintenance)(/|$) {
    root /var/www/platform/public;
    try_files $uri /index.php?$query_string;
}
# ثم الآبار:   location ^~ /api/wells/  { root /var/www/platform/public; try_files $uri /index.php?$query_string; }
# ثم السائق:   location ^~ /api/driver/ { ... }   location ^~ /api/map/ { ... }
# الرجوع: حذف الكتلة وإعادة تحميل nginx.
```

5. بعد كل تحويل: مراقبة `storage/logs` للمنصة (أخطاء 5xx، `driver.trip_sync.confirm`) وعدد الرحلات المؤكدة يومياً مقارنة بالأيام السابقة.
